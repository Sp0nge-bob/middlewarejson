# Проверка проекта A → B для Happ на iPhone

Дата: 24 октября 2026 года. Статус: совместимость конечной схемы НЕ ПОДТВЕРЖДЕНА.

## Результат углублённой проверки

Проверены не только поля Xray, но и цепочка доставки:
3x-ui v3.10.2 → HTTP middleware → преобразование IOS-FIX → импорт Happ → ядро.
В этой цепочке обнаружены самостоятельные проблемы трёх уровней:

1. Панель отдаёт A и B отдельными профилями; для автоматического приоритета
   требуется их композиция в один runtime-профиль.
2. Текущий IOS-FIX разрушает служебный fallback предлагаемой схемы;
   beta дополнительно нарушает порядок повторной маршрутизации DNS.
3. Есть отчёт с точным совпадением Happ 6.0.0 / API 4.1.0 / Xray 26.9.9
   о зависаниях XHTTP в мобильной сети. Его причина относится к HTTP/2 ядра
   и не устраняется перестановкой полей JSON.

Схему leastPing A → проверка оставшихся A → leastPing B можно проектировать
на доступных компонентах upstream v26.9.9. Однако объявлять готовый профиль
совместимым с эталонным Happ до проверки на устройстве оснований нет.
Код приложения и тестов в ходе этого исследования не изменялся.

Это аудит относящихся к задаче проблем, а не утверждение, что найдены все
существующие дефекты закрытого приложения и всех транспортов Xray.

## Как именно 3x-ui v3.10.2 отдаёт JSON

Сверены GetJson, appendBalancerEntries, buildBalancerConfig, streamData,
tlsData, HTTP controller, ClientQrModal и backend генерации Happ-ссылки.

### Контейнер подписки и состав профилей

- GetJson получает узлы по subId, учитывает исключения из подписки и
  формирует пользовательские конфигурации. Балансеры строятся из уже
  сформированных outbound этого подписчика, а не из всех серверов панели.
- К обычным профилям добавляется отдельный документ каждого включённого
  балансера, у которого нашлись участники. Затем документы сортируются.
  Поэтому нельзя считать «первый элемент массива = A, второй = B».
- Один элемент возвращается объектом, если alwaysReturnArray=false;
  иначе получается массив. В массиве могут присутствовать обычные узлы,
  балансеры, внешние подключения и информационный SOCKS-профиль.
- Внешние подключения добавляются после сборки балансеров: автоматически
  участниками этих балансеров они не становятся.
- Истёкшая/исчерпанная подписка может быть заменена информационным профилем.
  Отсутствие A/B в таком ответе нельзя трактовать как повод восстановить
  сохранённые ранее пользовательские credentials или обойти ограничения панели.

### Внутренность одного балансера

Для балансера с ID=12 реальные участники получают теги bal-12-vless,
bal-12-vless-2 и т. п. Суффикс отражает протокол и порядок выдачи, а не
постоянный ID конкретного сервера. Не хранить соответствие сервера по суффиксу.
Сам балансер имеет тег balancer, selector=["bal-12-"]. У другого документа
снова может быть balancer: одинаковые теги допустимы между документами,
но при слиянии требуют устранения коллизий.

Для leastPing и leastLoad панель выдаёт верхнеуровневый burstObservatory,
охватывающий префикс участников. По умолчанию: interval=1m, sampling=2,
timeout=5s, HEAD, connectivity="". fallbackTag указывает на первого участника.
Это означает попытку того же сервера при отказе проб, а не переход к другому
балансеру. Комментарий панели о необходимости именно burst не устанавливает
ограничение ядра: upstream leastPing читает общий интерфейс Observatory,
который реализует также обычный observatory.

Панель берёт общий baked-шаблон, заменяет правила outboundTag=proxy на
balancerTag=balancer, оставляет direct/block и добавляет системные outbounds.
У leastLoad могут быть привязанные к точным тегам regexp costs.
Переименование участников без изменения costs повредит такую конфигурацию.

### Что панель уже исправляет до middleware

Штатный default.json содержит первым SOCKS на 127.0.0.1:10808, но с tag=mixed;
далее HTTP на 127.0.0.1:10809. Sniffing всё ещё включает fakedns.
DNS по умолчанию — объект с address=8.8.8.8; policy/stats присутствуют.

В streamData панель убирает серверные sockopt и acceptProxyProtocol,
для XHTTP удаляет ряд серверных полей. tlsData уже поднимает клиентские TLS
поля из panel-shaped settings на правильный уровень: fingerprint,
verifyPeerCertByName, echConfigList, pinnedPeerCertSha256. Pins выдаются
строкой через запятую, что соответствует TLSConfig upstream v26.9.9.
Для Vision генVless отдельно обрабатывает TCP Mux; эти исправления нужно сохранить.

Новый компоновщик должен брать готовые клиентские outbounds, включая host/path,
TLS/SNI/ALPN, credentials и параметры XHTTP/gRPC/WS. Повторное построение их
из inbound панели создаст лишнюю точку несовместимости.

### HTTP, формат и ссылка импорта

Прямой JSON endpoint может отвечать Content-Type=text/plain; режим view=raw
отдаёт application/json. Автодетект на обычном subscription endpoint зависит
от User-Agent и настроек. Определять JSON только по Content-Type нельзя.
Accept=application/json сам по себе не гарантирует выбор нужного формата.

ClientQrModal строит JSON URL как subJsonURI + subId. Но backend
internal/web/service/happ.go в currentSource строит crypt5 из **subURI + subId**,
а не subJsonURI. Поэтому замены одного subJsonURI недостаточно для гарантии,
что штатная Happ QR-ссылка попадёт в middleware. Нужно согласовать фактический
URL импорта: прямая middleware JSON-подписка либо проверенный маршрут обычной
ссылки через middleware. Существующий автодетект панели может выдать JSON,
но это не обеспечит прохождение через middleware, если URL ведёт прямо в панель.

Controller перед выдачей JSON выполняет HWID-проверку. Он читает X-HWID,
X-Device-OS, X-Ver-OS, X-Device-Model; возвращает диагностические X-Hwid-*.
Текущий middleware эти request/response headers не пропускает. Если HWID
включён в панели, это отдельный конфликт доставки, существующий до балансировки.

ApplyCommonHeaders добавляет subscription metadata, Routing и Happ headers.
Middleware пропускает базовые поля и Routing, но отбрасывает ProviderID,
Hide-Settings и остальные расширенные параметры. Расширять разрешённый набор
следует по реально используемым полям. fallback-url/new-url, если используются,
должны указывать на совместимую выдачу, иначе обновление обойдёт преобразование.

[default.json](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/sub/default.json),
[controller.go](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/sub/controller.go),
[ClientQrModal](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/frontend/src/pages/clients/ClientQrModal.tsx),

## Сравнение IOS-FIX с требованиями нового профиля

Проверен текущий рабочий файл app/transformers/ios_fix.py, включая имеющиеся
до аудита локальные изменения. Название режима не означает автоматический
детектор iOS: TransformService применяет выбранный режим глобально по настройке.

| Механизм | Что делает текущий IOS-FIX | Оценка для эталона и требуемое изменение |
| --- | --- | --- |
| Первый inbound | mixed → socks; tag mixed → socks | Консервативную совместимость сохранить. В 3x-ui 3.10.2 protocol уже socks. Контролировать loopback listen и ссылки на изменённый tag. Не менять порты произвольно. |
| Bind | Не добавляет listen | Для штатного шаблона 3.10.2 уже исправлено панелью. Для кастомного шаблона проверять явно. |
| Sniffing FakeDNS | Удаляет точную строку fakedns из destOverride | Подходит штатному шаблону без FakeDNS. При реальном FakeDNS нужна отдельная политика; безусловное удаление меняет его работу. |
| Вложенный TLS | Удаляет settings, переносит только fingerprint и verifyPeerCertByName | На штатном новом JSON в основном избыточно: поля уже плоские. Для старого/кастомного JSON теряет вложенные pins/ECH. Нужна нормализация по схеме ядра с сохранением проверки сертификата. |
| verifyPeerCertByName | Удаляет фиктивные 0/false/null/none/пустое значение | Сохранить узкую очистку невалидного наследия с проверкой типа. В 26.9.9 поле строковое; корректные имена не заменять и не отключать проверку TLS. |
| WS heartbeatPeriod=0 | Удаляет поле | В схеме 26.9.9 uint32, отсутствие и 0 дают одинаковое значение. Это совместимость формата; доказательства обязательности для Happ 6.0.0 нет. Ненулевые heartbeat сохранять. |
| leastPing | Приводит имя стратегии, добавляет fallback на первый узел, заменяет burst обычным observatory | Нормализацию имени сохранить. В составном профиле fallback задавать по роли: A → guard, B → blackhole. Первый узел A как fallback недопустим. |
| leastLoad | Сохраняет settings, создаёт burst | Для задачи минимального RTT не нужен. Не включать чужие leastLoad-профили в общий ordinary-монитор без явного решения. |
| roundRobin/random | Всегда удаляет fallbackTag | Для служебного guard это разрушает A → B. Сохранить его fallback и подключить общий ordinary observatory. Старый кейс без наблюдателя учитывать отдельно. |
| Неизвестная стратегия | Превращает в random | В приоритетном режиме отклонять неподдерживаемую схему с диагностикой; молчаливая случайная маршрутизация нарушает контракт. |
| Мониторы | Удаляет все старые ordinary/burst и пересобирает один | Новый профиль собирать с одним согласованным ordinary для реальных A/B. Не запускать старую пересборку поверх готового графа. |
| Параметры проб | Interval=20s, burst timeout=5s, HEAD; сохраняет sampling | Это изменение политики панели, а не только парсера. Явно фиксировать политику; ordinary GET и burst HEAD измеряют немного разные пути. |
| Probe URL | Меняет любой URL с подстрокой google.com | Для нового режима проверять scheme/hostname и использовать явно заданный HTTPS endpoint. Подстрока может встречаться в path/query чужого URL. |
| Поиск fallback-кандидата | Исключает freedom/blackhole/dns, но не loopback | Разрешать только реальные A/B. Служебные теги не должны попадать в selector/пробы или резерв первого участника. |
| Beta DNS | Добавляет port=53 первым, выбирает первый balancer | Поведение направления DNS через VPN обязательно сохранить в новом режиме. Служебные inboundTag-правила должны идти раньше DNS. Выбирать pool A по роли, а не положению в массиве; учитывать существующие условные DNS-правила. |
| Валидация | Проверяет наличие массива outbounds | Нужна проверка связности tags/selectors/fallback/rules, непустых пулов, ссылок и отсутствия циклов. |
| Передача HTTP | Сохраняет UA и базовые response headers | При включённых HWID/Happ management согласовать конкретные дополнительные headers. Бинарные возможности по строке API 4.1.0 не угадывать. |

Принцип реализации: выделить безопасную нормализацию одного профиля и отдельную
сборку приоритетного графа. Переиспользование apply_ios_fix целиком после сборки
графа не подходит. Не следует глобально менять fingerprint, ALPN, транспорт,
Mux или параметры проверки сертификатов в попытке исправить неопределённый баг.

## Проблемы версии и степень подтверждения

### XHTTP / HTTP2: точное совпадение Happ 6.0.0

[Happ #8](https://github.com/Happ-proxy/.github/issues/8) описывает именно
Happ 6.0.0 / API 4.1.0 / Xray 26.9.9, iPhone 15 Pro, T2, XHTTP packet-up:
замирания в мобильной сети при работоспособности того же узла по Wi-Fi.
Воспроизведение — пользовательский отчёт, не наш запуск и не подтверждение
того, что каждый iPhone с этой версией испытывает такой отказ.

Связанный [Xray #6797](https://github.com/XTLS/Xray-core/issues/6797)
содержит измерения роста числа физических TLS-соединений вопреки
xmux.maxConnections в Go 1.27-сборках. Термин «утечка памяти» не считать
установленным: в обсуждении его оспаривают. Подтверждается проблема dial
coalescing, а память и зависания — возможные последствия конкретной нагрузки.

Проверка исходников: upstream v26.9.9 использует go 1.27 и x/net v0.58.0;
XHTTP dialer создаёт http2.Transport. В x/net v0.60.0 добавлено восстановление
объединения параллельных dial, подтверждённое
[коммитом 01e3d033](https://github.com/golang/net/commit/01e3d0338c2256320c59c863f9298e9544a99feb).
Обновления Xray [#7133](https://github.com/XTLS/Xray-core/pull/7133) и
[#7147](https://github.com/XTLS/Xray-core/pull/7147) merged; проверенный
upstream v26.10.21 уже содержит x/net v0.61.0. В issue есть сообщение об
исправлении с 26.10.17, однако такой tag через GitHub API не найден:
версионное утверждение фиксируем как сообщение участника, а наличие патча
подтверждаем по доступному тегу v26.10.21. Обновление upstream не означает,
что исправленная библиотека уже встроена в установленный Happ.

Для старых сборок в обсуждении работает компиляция с -tags http2legacy.
Это build flag, его нельзя добавить в JSON-подписку. Менять xmux.maxConnections
и обещать исправление эталонного 26.9.9 на этом основании нельзя.

Влияние на A → B: правильный выбор B ещё не гарантирует, что фоновые пробы
заблокированных XHTTP A перестанут создавать нагрузку. Приоритетный граф
должен квалифицироваться вместе с реальными транспортами и ресурсами extension.
WS/gRPC через собственный TLS/Nginx можно рассматривать только как отдельно
проверенные существующие серверные варианты; произвольно менять network в JSON
без совместимого inbound сервера нельзя. Vision не является рекомендацией
заменить согласованную архитектуру пользователя.

### Таймаут внешней пробы не равен отмене транспортного dial

[Xray #6591](https://github.com/XTLS/Xray-core/issues/6591) сообщает о зависших
goroutines при молчащем TLS peer, отдельно на стороне burst-пробы и outbound.
В v26.9.9 burst/ping.go действительно не устанавливает TLSHandshakeTimeout,
а ordinary observer.go задаёт 5s. Это дополнительный аргумент в пользу ordinary
для исходного iOS-варианта, но не доказательство отсутствия всех зависаний.

[Xray #6590](https://github.com/XTLS/Xray-core/issues/6590) отдельно относится
к XHTTP dial. В проверенном v26.9.9 client.go использует context.WithoutCancel;
taggedimpl возвращает dispatched connection без отдельного cancel-on-close.
HTTP timeout наблюдателя не даёт основания обещать освобождение всех внутренних
попыток соединения. Issues описывают воспроизводимые специальные условия;
подтверждения их проявления на эталонном iPhone в нашем проекте нет.

Следствие: не уменьшать интервалы до агрессивных значений без проверки.
enableConcurrency=true обеспечивает своевременный охват A/B, но число одновременных
проб растёт с количеством узлов. Обычный observatory 26.9.9 не предоставляет
настраиваемый лимит параллелизма или отдельное расписание A/B.

### Исторические iOS/loopback-проблемы

3x-ui #3718/#6379 подтверждают полезность SOCKS/bind в конкретных версиях;
они не доказывают отказ mixed во всех Happ. Штатный 3.10.2 уже содержит SOCKS
и loopback bind. Изменение тега inbound без обновления ссылок остаётся нашей проблемой.

Xray #5710/PR #5836 и #5958/PR #5960 касаются nil inbound и изменения общего
inbound context в loopback. Оба исправления присутствуют в upstream v26.9.9.
Приписывать их эталонному телефону только по старому Happ fork неправильно.

## DNS и Happ Routing: два разных слоя

### Согласованное требование: сохранить поведение ios-fix-dns

Пользователь подтвердил: в обновлении сохранить направление DNS через балансер.
Для TCP/UDP на порт 53, попавших в Xray, новый профиль должен явно направлять
трафик в cf-pool-a и далее по общей приоритетной схеме:

- Есть доступный A → leastPing выбирает A с минимальной измеренной задержкой.
- Все A признаны недоступными → служебный guard переводит трафик в leastPing B.
- A восстановился → новые DNS-соединения/сессии снова используют A.
- Недоступны оба пула → blackhole; автоматического выхода DNS через direct нет.

Обязательный порядок: два служебных inboundTag-правила loopback, затем правило
network=tcp,udp / port=53 / balancerTag=cf-pool-a, затем остальные пользовательские
правила. После loopback DNS должен попасть в cf-a-check или cf-pool-b, минуя
повторный захват общим DNS-правилом. Вставку правила на абсолютную позицию 0
из нынешней beta переносить нельзя. Любое условное правило с port=53 не считать
полной заменой этого маршрута: проверять его охват и целевой balancer.

Назначение — уменьшить риск прямого выхода обычного DNS мимо VPN. Это правило
не перехватывает запросы вне Xray и не определяет маршрут DoH/DoT; они зависят
от Tunnel DNS и остальных правил. Не обещать сокрытие самого VPN или полное
отсутствие DNS-утечек на основании одного port=53. Если существующий общий
маршрут уже охватывает DNS через балансер, отдельное правило может не менять
фактический путь, но требуемая политика должна быть сохранена.

### Отдельные настройки приложения и ядра

Публичные Happ dev-docs описывают текущее поведение, но не дают полной
версионной спецификации именно binary 6.0.0. Согласно документации:

- JSON-подписка имеет 0 или 1 связанный Routing профиль, доставленный провайдером.
- Tunnel DNS задаётся приложением отдельно от DNS-блока фактического Xray JSON.
- dns-from-json-enable использует первый dns.servers только без Routing профиля;
  IP/объект/DoH обрабатываются по-разному. Для DoH документация требует IP в hosts;
  невалидное значение на iOS приводит к запасному Cloudflare DoH.
- fallback-url относится к загрузке подписки. subscriptions-sort-type=ping
  сортирует список в UI; это не балансировка пользовательских соединений.

Нужны три самостоятельные проверки: bootstrap адресов A/B до установления
соединения, DNS-запросы приложений внутри туннеля, DNS/HTTPS probe endpoint на
выходе каждого узла. Beta port=53 не решает автоматически bootstrap, DoH и
настройку DNS системного туннеля. В частности, DNS default.json=8.8.8.8 не
доказывает доступность этого адреса на клиентской сети с белыми списками.

Источники: [Happ routing](https://github.com/HappDev/happ_su/blob/main/dev-docs/routing.md),
[app management](https://github.com/HappDev/happ_su/blob/main/dev-docs/app-management.md),
[ping](https://github.com/HappDev/happ_su/blob/main/dev-docs/ping.md).

## Требуемая последовательность реализации

Пользователь изменил способ выбора пулов: вместо настройки ID использовать
служебные метки в верхнеуровневом remarks профилей балансеров. Примеры:
[A] Обычные сервера и [B] БС сервера. Панель выдаёт balancer.Remark как remarks
документа, поэтому метка доступна middleware без дополнительного API-запроса.

Контракт распознавания: точные метки в квадратных скобках в любой позиции,
без учёта регистра; [A]/[А] определяет A, [B]/[В] определяет B. Латинские и
кириллические варианты поддерживаются явно; произвольный текст после/до метки
не определяет роль. Маркеры искать только в remarks документа-балансера.
Нужны ровно один A и один B и корректная структура routing.balancers/selectors.
Метка сама по себе не делает одиночный proxy-профиль балансером.

Если одной роли нет, роль продублирована или в одном названии обе роли,
композицию не выполнять, профили оставить отдельными с диагностикой. Если
меток нет вообще, композиция не применяется. Не выбирать первую пару и не
достраивать отсутствующий пул из остальных узлов. Итоговое имя составного
профиля не содержит этих меток; служебный граф распознаётся отдельно для
идемпотентной обработки. bal-<ID>- остаётся внутренним префиксом участников,
но ID не требуется задавать в настройках middleware.

1. Зафиксировать правила меток remarks и точный middleware URL импорта.
2. Разобрать объект/массив панели; выбрать однозначную пару по меткам remarks,
   затем проверить балансы, selector и реальные outbounds. Позицию в массиве
   и произвольную часть названия не использовать для определения роли.
3. Разрешить участников в реальные endpoints/credentials; проверить, что группы
   непустые и не содержат один и тот же фактический узел под разными тегами.
   При конфликте DNS/routing/policy двух шаблонов не выбирать один молча.
4. Выполнить узкую iOS-нормализацию inbound/TLS, сохранить transport и stats/policy.
5. Собрать один граф leastPing A → roundRobin guard → leastPing B, два loopback
   и терминальный blackhole. От первого участника A как аварийного резерва отказаться.
6. Создать один ordinary observatory с selector только реальных A/B. Служебные
   маршруты поставить раньше DNS/direct/block, а пользовательские исключения
   сохранить перед обычным proxy catch-all. Сохранить beta DNS-маршрут:
   TCP/UDP port=53 → cf-pool-a, после служебных loopback-правил. Проверить все
   ссылочные поля, переход DNS A → B, возврат в A и отсутствие прямого fallback.
7. Не запускать старый _fix_panel_balancer поверх этого графа. Повторная обработка
   готового профиля должна быть идемпотентной.
8. Согласовать HWID/metadata/доставку DNS и Routing headers. Проверить import,
   refresh, refresh существующего профиля и rollback на старый режим.
9. Выполнить регрессионные проверки генератора и запустить конечный профиль
   на целевом iPhone с реальными транспортами. Включить обнаружение меток,
   кириллицу/латиницу, дубликаты, неполную пару и смену ID балансеров.
   Одного xray -test недостаточно.

Контракт «все A недоступны» означает все отрицательные результаты актуальных
наблюдений, а не знание физического состояния сети в реальном времени. При
пустом отчёте guard оставляет неизвестные A кандидатами; возможна ошибка первого
соединения до измерения. Возврат к A происходит после новой успешной пробы.
Открытые TCP/UDP-сессии не мигрируют между узлами. leastPing выбирает минимальную
измеренную задержку HTTPS-пробы, а не максимальную пропускную способность.

## Подтверждённые конфликты локальной прослойки

1. apply_ios_fix на структурном фрагменте проекта удаляет fallbackTag у cf-a-check.
   Результат проверки: guard_fallback=null, observatory=true,
   burstObservatory=false. Связь от защитного балансера к группе B теряется.
2. apply_ios_fix_dns дополнительно ставит правило port=53 → cf-pool-a первым,
   перед cf-enter-a-check и cf-enter-pool-b. После исправления пункта 1 это
   создаёт риск петли для DNS: loopback вернётся к тому же раннему DNS-правилу.
3. Текущий режим leastPing пересобирает обычный observatory. Прежний проект,
   основанный на burstObservatory, не соответствовал этому контракту.
4. _fix_first_inbound меняет mixed → socks и tag mixed → socks, но не добавляет
   listen=127.0.0.1 и не переписывает ссылки routing.rules.inboundTag.
   У v3.10.2 шаблон уже содержит loopback listen и protocol=socks, однако это
   нужно контролировать и при пользовательских шаблонах.

Эти результаты устанавливают несовместимость текущего преобразования с новым
графом. Они не доказывают отказ самой библиотеки Happ на iPhone.

## Что подтверждается исходниками ядра

- leastPing берёт доступный узел с минимальным Delay из наблюдений своего пула.
- roundRobin с непустым fallbackTag запрашивает extension.Observatory,
  исключает Alive=false и оставляет узлы, отсутствующие в отчёте.
- Поэтому промежуточный roundRobin при наличии общего наблюдателя может отличать
  «нет успехов, остались непроверенные A» от «все A исключены».
- Обычный observatory поддерживает параллельные проверки, использует отдельный
  outbound для каждой пробы и реализован в публичном форке Happ.
- Loopback присутствует в main/distro/all и реализации proxy/loopback этого форка.
  Это подтверждает наличие исходников компонента, но не состав конкретного xcframework.

## Issues: что из них следует

### 3x-ui #3718 и #6379: iOS подключён, трафик не проходит

Есть пользовательские отчёты, в которых замена mixed → socks восстанавливает
трафик; в #6379 опубликован сравнительный эксперимент на Happ 5.6.0 iOS.
В комментариях #3718 описан также рабочий mixed с явным listen=127.0.0.1.
Следовательно, нельзя объявлять mixed принципиально неподдерживаемым протоколом
на всех iPhone. Консервативный вариант: SOCKS первым, явный loopback listen.

### 3x-ui #6417: bind и Vision/Mux

Описаны нулевой трафик из-за отсутствия loopback listen и ошибка TCP Mux при
Vision. 3x-ui v3.10.2 уже содержит listen=127.0.0.1 в default.json и обработку
TCP Mux для flow в genVless. Исправления панели нужно сохранять при слиянии профилей.

### 3x-ui #2724: not all dependencies are resolved

Сообщение касается Xray 25.3.3 и roundRobin/random с fallbackTag, которые требуют
наблюдателя. Issue не является доказательством несовместимости такого балансера
с iOS при корректно подключённом наблюдателе. Удалять fallback служебного a-check
нельзя: нужно удовлетворить зависимость одним обычным observatory.

### Xray #5710 / PR #5836: nil inbound в loopback

Исправление добавляет обработку отсутствующего session.Inbound в контексте.
Исходная гипотеза автора issue про nil config не совпадает с фактическим патчем.
Сценарий репортера использовал proxySettings; он не идентичен нашему routing fallback.
Проверенный старый публичный форк Happ не содержит этого исправления.
В эталонном upstream v26.9.9 соответствующая защита уже присутствует.

### Xray #5958 / PR #5960: loopback меняет общий inbound context

Воспроизведён ошибочный выбор маршрутов при fallback через loopback с Mux.
Патч создаёт копию session.Inbound перед заменой Tag. В проверенном форке Happ
сохранилось изменение исходного объекта на месте и отсутствует этот патч.
В эталонном upstream v26.9.9 копирование контекста уже реализовано; старый форк
не является подходящим основанием приписывать этот баг Happ 6.0.0/Xray 26.9.9.
Отключение Mux в первом прототипе упрощает проверку; не является универсальным
доказанным исправлением всех проблем loopback.

## Уточнение проекта для iOS

Базовая схема остаётся leastPing A → a-check → leastPing B, со служебными loopback.
В базовом iOS-варианте используется один обычный observatory с охватом A и B:

```json
{
  "observatory": {
    "subjectSelector": ["cf-a-", "cf-b-"],
    "probeUrl": "https://www.gstatic.com/generate_204",
    "probeInterval": "20s",
    "enableConcurrency": true
  }
}
```

Burst не объявляется неработающим на iOS: для него просто нет достаточного
подтверждения в целевой сборке, а существующий leastPing ios-fix использует ordinary.
Нельзя одновременно создавать observatory и burstObservatory для одного графа.

Предлагается отдельная обработка приоритетного профиля с сохранением существующих
исправлений inbound/TLS. В ней нельзя применять общую ветку, удаляющую fallbackTag
у a-check. Служебные правила loopback должны предшествовать DNS-правилу beta.

## Минимальная проверка на целевом iPhone

Зафиксировать Happ/Happ RU, номер версии и build, iOS, версию ядра из диагностики.
Проверять последовательные профили, чтобы локализовать отказ:

1. Один обычный A через минимальный профиль с iOS-исправлениями.
2. Несколько A + leastPing + ordinary observatory: проверить фактический узел выхода.
3. Один принудительный loopback-переход к B: проверить TCP, DNS и UDP.
4. Полный профиль A → a-check → B, все A доступны.
5. Отключить A по одному; B не должен использоваться до отказа последнего A.
6. Отключить все A при нескольких доступных B; проверить выбор минимального RTT B.
7. Восстановить один A; проверить возвращение новых соединений в A.
8. Проверить A с 300/300/2000ms, затем отказ быстрых A: медленный доступный A
   должен сохранять приоритет перед B, если не вводить отдельную RTT-политику.
9. Переключить Wi-Fi/LTE, заблокировать экран, проверить возобновление и фон.
10. Повторить DNS/UDP и проверку маршрутов с используемыми в production настройками Mux.
11. Для DNS TCP и UDP отдельно проверить маршрут через быстрый A, сохранение A
    при отказе одного участника, переход к B после отказа всех A и возврат новых
    сессий к A. При отказе обоих пулов не должно быть прямого DNS fallback.
    Убедиться, что повторная маршрутизация через loopback не создаёт DNS-петлю.

Критерий — реальный узел выхода/новые соединения, журналы и счётчики на узлах.
Проверочные запросы Observatory сами создают трафик к B, даже когда пользовательский
трафик идёт через A; поэтому ненулевой счётчик B сам по себе не означает нарушение.
CONNECTED в UI, ping списка узлов и успешный парсинг JSON не подтверждают весь сценарий.
