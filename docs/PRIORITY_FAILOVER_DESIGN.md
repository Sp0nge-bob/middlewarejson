## Контракт 3x-ui v3.10.2

buildBalancerConfig формирует отдельный JSON-документ для каждого балансера.
Его реальные узлы получают префикс bal-<ID>-, а сам балансер внутри документа
имеет общий тег balancer. Два отдельных документа в массиве подписки не образуют
общий runtime-балансер Xray.

GetJson может вернуть объект или массив, содержащий также обычные узлы,
внешние подключения и информационные профили. Порядок зависит от сортировки
панели. Истёкшая подписка может содержать только информационный профиль.
Выбор A/B не должен зависеть от позиции элементов и не должен обходить
ограничения выдачи панели. Внешние подключения добавляются после сборки
балансеров и автоматически их участниками не становятся.

Согласовано с пользователем: выбирать два профиля по служебным меткам в
верхнеуровневом поле remarks, без настройки ID балансеров панели:

- [A] Обычные сервера → пул A.
- [B] БС сервера → пул B.

Распознавать точную метку в квадратных скобках в любой позиции remarks,
без учёта регистра. Поддерживать визуально похожие латинские/кириллические
буквы: [A]/[А] для A, [B]/[В] для B. Текст вне метки произвольный и не
определяет роль. Не искать маркеры в описаниях отдельных узлов или transport settings.

Сначала найти ровно один документ-балансер A и ровно один B. Затем проверить
структуру routing.balancers и разрешить его selector в реальные outbounds.
bal-<ID>- используется как внутренний префикс участников из выдачи панели,
а не как настроенный критерий выбора A/B. Метка у одиночного proxy-профиля
не превращает его в балансер. Два разных маркера в одном remarks, дубликаты
профилей одной роли или отсутствие пары не должны приводить к угадыванию:
не собирать составной профиль, оставить профили отдельными и записать диагностику.
При отсутствии обеих меток композиция не применяется. Нельзя автоматически
считать все остальные узлы подписки отсутствующим пулом.

Middleware извлекает только доступные этому подписчику реальные узлы
и создаёт один составной профиль. Исходные параметры подключений сохраняются.
Итоговому профилю дать отдельное имя без маркеров [A]/[B]; повторную обработку
готовой служебной схемы определять по её структуре и зарезервированным тегам.
Имя настраивается ALLOWLIST_BALANCER_NAME; флаг перед именем задаётся отдельно
двухбуквенным ALLOWLIST_BALANCER_FLAG (RU/NL/DE/EU, пусто — без флага).
Оба значения доступны через CLI/SQLite без перезапуска и не влияют на роли пулов.
Префиксы уже уникальны между балансерами, поэтому без необходимости переименовывать
реальные outbounds не нужно. Служебные pool-A/pool-B получают отдельные теги.

Общие DNS/inbounds/direct/block берутся из совместимого шаблона A; конфликты
системных outbounds или параметров DNS между документами требуют диагностики.
Их нельзя молча склеивать или выбирать случайно. Одиночные и несвязанные профили
подписки могут сохраняться, но автоматический выбор работает внутри нового
составного профиля, который пользователь выбирает в Happ.

Штатный fallbackTag панельного leastPing/leastLoad указывает на первый узел того
же балансера, даже если все проверки неудачны. Его заменяет явная связь A → B.
Панель по умолчанию выдаёт burstObservatory с interval=1m, sampling=2,
timeout=5s, httpMethod=HEAD и connectivity="". Для быстрого переключения параметры
наблюдения задаются отдельно настройками функции БС-балансера.

## Требование

A — обычные VPN-серверы. B — VPN-серверы, доступные пользователю в режиме белых списков.

Для каждого нового соединения выбирать A, пока в A есть хотя бы один узел,
который не признан недоступным. Переходить к B только тогда, когда каждый узел A
имеет отрицательный результат клиентской проверки. В B также выбирать доступные
узлы. При восстановлении любого A следующие соединения снова направлять в A.

Решение принимается Xray внутри Happ на устройстве. Middleware формирует
конфигурацию при обновлении подписки; повторное обновление для переключения не нужно.

Это политика доступности: отказ всех A по любой причине включает B.

## Архитектура

Один JSON-профиль содержит реальные outbounds обеих групп, три балансера,
два служебных loopback outbound и один blackhole outbound.
Основной выбор внутри обеих групп выполняется leastPing.

Путь пользовательского VPN-трафика:

```text
обычные routing rules → pool-A (leastPing) → A с минимальным измеренным RTT
                          |
                          | нет положительных наблюдений A
                          v
                     to-a-check (loopback)
                          |
                     a-check (roundRobin)
                          |
                          ├─ есть непроверенный A → пробовать A на запуске
                          |
                          └─ все A имеют Alive=false
                                         |
                                    to-pool-B (loopback)
                                         |
                                    pool-B (leastPing)
                                         |
                                         ├─ B с минимальным измеренным RTT
                                         └─ нет доступного измеренного B → blackhole
```

Правила для служебных inboundTag после loopback располагаются перед обычными.
Ни одно правило B не возвращает трафик в A. Реальные outbounds A/B не используют
этот loopback как dialerProxy: каждый проверяется через собственное соединение.

Существующие direct/block-исключения сохраняются. Только правила, которые раньше
направляли пользовательский трафик в модернизируемый балансер, направляются в pool-A.

## Выбор стратегии и запуск

Для обоих пулов используется leastPing + fallbackTag + общий observatory.
Измерение задержки определяет выбор внутри группы, а связь fallback задаёт
приоритет группы A перед B. Быстрый B не конкурирует с доступным A.

Дополнительный балансер a-check использует roundRobin на том же наборе реальных A.
Он нужен только когда основной leastPing не нашёл ни одного положительного
наблюдения. Он исключает Alive=false и оставляет ещё не проверенные узлы.
Таким образом, пустой отчёт leastPing не включает B: сначала a-check проверяет,
остался ли хотя бы один кандидат A. К B ведёт только пустой набор a-check.

В установившемся состоянии с положительными наблюдениями leastPing сразу
направляет трафик на самый быстрый известный A; a-check в этом пути не участвует.
На запуске, пока положительных измерений нет, a-check выбирает непроверенные A
по очереди. Их задержка ещё неизвестна; выбрать самый быстрый без измерений нельзя.

При изменении отчёта между двумя последовательными выборами возможен переходный
случай: leastPing не увидел живых A, затем a-check увидел уже восстановившиеся A
и выбрал один из них по очереди. Выбор не является атомарным снимком отчёта.
Следующие обычные выборы снова идут напрямую через leastPing.

Состояния A:

| Состояние | Поведение |
| --- | --- |
| Все ещё не проверены | Начать с A; запустить проверки |
| Есть успешные A | Использовать A с минимальным измеренным RTT |
| Часть A отказала, есть непроверенный A | Продолжать выбирать среди оставшихся A |
| Все A имеют статус Alive=false | Перейти в балансер B |
| После перехода восстановился хотя бы один A | Новые соединения снова идут в A |

Например, при актуальных успешных наблюдениях A1=300ms, A2=300ms, A3=2000ms
leastPing выбирает A1 или A2; A3 не выбирается, пока существует более быстрый
доступный A. При равном RTT нельзя обещать равномерное распределение.

На запуске пользовательское соединение может попасть на ещё не проверенный A
и получить ошибку. Ожидание полной первой проверки до открытия туннеля требует
поддержки в самом клиенте; обычная JSON-конфигурация такой барьер не предоставляет.

## Каркас конфигурации

Согласовано с пользователем: в составном профиле сохранить поведение ios-fix-dns —
направление TCP/UDP DNS на порт 53 через общую приоритетную балансировку A → B.
Служебные loopback-правила должны идти раньше этого DNS-правила.

Ниже структурный фрагмент, не самостоятельная конфигурация. Реальные outbounds
и inbounds берутся из 3x-ui. В примере реальные узлы уже получили уникальные
теги с префиксами cf-a- и cf-b-.

```json
{
  "outbounds": [
    {
      "tag": "cf-to-a-check",
      "protocol": "loopback",
      "settings": { "inboundTag": "cf-enter-a-check" }
    },
    {
      "tag": "cf-to-pool-b",
      "protocol": "loopback",
      "settings": { "inboundTag": "cf-enter-pool-b" }
    },
    {
      "tag": "cf-unavailable",
      "protocol": "blackhole",
      "settings": {}
    }
  ],
  "routing": {
    "rules": [
      {
        "type": "field",
        "inboundTag": ["cf-enter-a-check"],
        "balancerTag": "cf-a-check"
      },
      {
        "type": "field",
        "inboundTag": ["cf-enter-pool-b"],
        "balancerTag": "cf-pool-b"
      },
      {
        "type": "field",
        "port": 53,
        "network": "tcp,udp",
        "balancerTag": "cf-pool-a"
      },
      {
        "type": "field",
        "network": "tcp,udp",
        "balancerTag": "cf-pool-a"
      }
    ],
    "balancers": [
      {
        "tag": "cf-pool-a",
        "selector": ["cf-a-"],
        "strategy": { "type": "leastPing" },
        "fallbackTag": "cf-to-a-check"
      },
      {
        "tag": "cf-a-check",
        "selector": ["cf-a-"],
        "strategy": { "type": "roundRobin" },
        "fallbackTag": "cf-to-pool-b"
      },
      {
        "tag": "cf-pool-b",
        "selector": ["cf-b-"],
        "strategy": { "type": "leastPing" },
        "fallbackTag": "cf-unavailable"
      }
    ]
  },
  "observatory": {
    "subjectSelector": ["cf-a-", "cf-b-"],
    "probeUrl": "https://www.gstatic.com/generate_204",
    "probeInterval": "20s",
    "enableConcurrency": true
  }
}
```

При встраивании в реальный профиль catch-all в примере не должен вытеснять
существующие DNS/direct/block-правила. Служебные правила a-check и B идут первыми,
затем согласованное DNS-правило, затем остальные пользовательские правила.
Первый outbound реального профиля стоит сделать cf-unavailable, чтобы неявный
маршрут по умолчанию не выпустил VPN-трафик напрямую при ошибке правил.

DNS использует самый быстрый измеренный доступный A; только после отказа всех A
переходит в leastPing B. При восстановлении A новые DNS-соединения/сессии снова
направляются в A. Отказ обоих пулов не должен приводить к DNS fallback через direct.
Наличие любого старого условного port=53-правила не заменяет проверку полного
охвата и правильной цели DNS-маршрута. Повторная обработка не создаёт дубли правил.

Это относится к DNS-трафику, попавшему в Xray. Tunnel DNS, bootstrap DNS и
маршруты DoH/DoT проверяются отдельно. Правило уменьшает риск прямого выхода
обычного DNS, но само по себе не гарантирует отсутствие всех DNS-утечек и не
скрывает факт VPN-соединения.

## Проверки доступности

Обычный observatory выполняет HTTPS-запрос отдельно через каждый реальный outbound,
то есть проверяет соединение телефона с VPN-узлом и дальнейший выход через него.
Недоступность одного A исключает только его; остальные A остаются кандидатами.
В проверенных исходниках upstream v26.9.9 observer.go использует HTTP GET с таймаутом 5s,
обновляет Alive по результату отдельной пробы и поддерживает enableConcurrency.
Начальный probeInterval=20s соответствует текущему ios-fix; суммарная задержка
обнаружения включает выполнение проб и ожидание. Нельзя обещать переход за 20s.
Для ordinary observatory нет sampling/httpMethod/connectivity в нашей конфигурации.

В v26.9.9 ordinary не проверяет status code и закрывает тело без полного чтения;
его Delay измеряет время до HTTP-ответа, а не скорость скачивания. Произвольный
HTTP-ответ без ошибки транспорта считается успехом. Для строгой проверки
кода/содержимого или голосования по нескольким адресам нужен другой механизм.

Таймаут запроса 5s не гарантирует отмену всех внутренних transport dial.
XHTTP использует WithoutCancel; #6590/#6591 описывают зависшие попытки при
молчащем TLS peer. Ordinary имеет TLSHandshakeTimeout=5s, в отличие от
burst/ping.go эталонного тега, но это не устраняет автоматически проблемы
dispatch/транспортов. Возобновляемые проверки недоступных A необходимо проверять
на рост памяти/соединений во время длительной работы через B.

Проверки A продолжаются при работе через B. Измеряются только реальные узлы,
без loopback/blackhole. Используется один монитор на весь составной профиль.
Параллельные проверки и количество узлов необходимо оценить в iOS Network Extension
на фактическом устройстве, включая фон, сон и смену сети.

Само наличие burstObservatory в исходниках не означает его несовместимость с iOS.
Его исключение из базового варианта — сохранение существующего контракта ios-fix
для leastPing, а не утверждение о запрете burst на всех iPhone.

### Вариант burstObservatory, не базовый для iOS

Начальные параметры: interval=10s, sampling=2, timeout=5s, httpMethod=HEAD.
В Happ HealthPing период планировщика равен interval × sampling, а отдельные
пробы распределяются случайно внутри этого периода. Есть отдельная начальная
проверка с одной пробой на узел. История узла хранит sampling результатов со
сроком актуальности 2 × interval × sampling. sampling=2 не означает обязательные
два последовательных отказа перед самым первым переключением.

Burst Observer выставляет Alive, когда среди актуальных результатов есть хотя бы
один успех. Если все актуальные результаты неудачны (или все результаты записи
устарели), Alive=false. RoundRobin исключает такие A; неизвестный, ещё не
представленный в отчёте A продолжает считаться кандидатом. Условие перехода —
исключены все реальные A, а не отказ одного A или превышение RTT.

10s не означает гарантированное переключение за 10s. Старый успешный результат
может задержать переход, а новый успешный результат позволяет вернуться к A.
Точные задержки зависят от истории, планировщика и встроенной в Happ версии ядра.

Probe URL должен быть стабильным HTTPS endpoint с маленьким ответом, доступным
со всех VPN-выходов. Отказ общего endpoint может ошибочно пометить обе группы
недоступными. Он должен иметь независимый мониторинг и отказоустойчивое размещение.
Изученный ping.go не проверяет HTTP status code: полученный HTTP-ответ без
транспортной ошибки считается успешной пробой. Код 204 — контракт нашего endpoint,
но клиентский механизм не проверяет его строго. Для HEAD тело не читается;
для GET чтение тела тоже входит в проверку. Требование строгой проверки ответа
или голосования по нескольким URL потребует другого клиентского механизма.

connectivity оставляем пустым: иначе после ошибки конкретного outbound ядро
проверяет прямой доступ к этому URL. Если URL тоже заблокирован, ошибка узла
может не попасть в историю (считается, что упала локальная сеть), и A может
дольше сохранять старое состояние. Это особенно существенно при белых списках.

Проверки A продолжаются и во время работы через B. Проверки B также идут заранее,
чтобы резерв имел актуальные результаты к моменту переключения.

Нативный burstObservatory использует окно результатов; он не реализует отдельные
настраиваемые пороги «три отказа подряд», «два успеха подряд» или минимальное время
пребывания в группе. Такие пороги не обещаются в этой версии проекта.

Выбор относится к новым соединениям и последним результатам проб. Уже открытые
соединения не переносятся на другой сервер, а результат проверки может устареть
между циклами. HTTP-проба не гарантирует работоспособность всех UDP-направлений.

   по меткам [A]/[А] и [B]/[В] в remarks, без конфигурации ID и без нового режима.
   Проверить однозначность ролей и структуру профилей. При отсутствии корректной
   пары или неоднозначности оставить профили отдельными; не собирать пул наугад.
2. Сначала разрешить selectors исходного балансера в конкретный набор outbounds.
   Проверить: обе группы непустые, не пересекаются и состоят из разрешённых
   пользователю реальных узлов. При отсутствии B оставлять профили отдельными
   с диагностикой; отсутствующий пул не достраивать из остальных серверов.
3. Не определять группу по флагу страны, задержке или типу Wi-Fi/LTE.
   Использовать явное соответствие тегов/групп из настроек.
4. Сохранить параметры подключений и пользовательские credentials из 3x-ui.
   Если теги переименовываются в cf-a-/cf-b-, обновить ссылки на них во всём
   поддерживаемом графе конфигурации; при неподдерживаемых ссылках отклонить
   преобразование с диагностикой, а не отдавать повреждённую конфигурацию.
5. Добавить два служебных loopback, blackhole и три балансера; сохранить остальные
   правила и балансеры, не связанные с преобразуемым профилем.
6. Сначала проверить исходную пару и собрать граф. Затем выполнить узкие
   iOS-исправления inbound/TLS. _fix_panel_balancer распознаёт и валидирует
   составной профиль, пропуская прежнюю пересборку fallback/observatory.
   _inject_routing_rules не меняет порядок служебных правил готового графа.
7. Формировать один согласованный блок наблюдения. Конфликт с несвязанными
   leastLoad/burstObservatory-конфигурациями требует явной политики совместимости;
   не удалять эти блоки молча.
8. Сохранить обработку subscription-заголовков и согласованное поведение IOS-FIX-DNS:
   TCP/UDP port=53 → cf-pool-a с переходом в B только после отказа всех A.
   Проверить, что Happ Routing не обходит эту схему. Служебные правила
   cf-enter-a-check/cf-enter-pool-b ставить перед DNS-правилом; иначе повторная
   маршрутизация DNS через loopback может снова попадать в основной pool-A.
   DNS-цель выбирать по роли, а не по первому балансеру в массиве.
9. Сделать преобразование идемпотентным: повторная обработка не создаёт новые
   loopback outbounds, правила или повторные префиксы тегов.
10. Для iOS сохранить первым локальный SOCKS inbound с listen=127.0.0.1.
    При изменении inbound tag обновлять ссылки routing.rules.inboundTag.
    Служебные loopback не должны становиться первым локальным inbound.
11. Сохранить fallbackTag промежуточного roundRobin и предоставить ему тот же
    observatory, что и leastPing. Ошибка #2724 связана с отсутствующей зависимостью
    наблюдателя, а не доказывает запрет roundRobin+fallbackTag при наличии наблюдателя.
12. Нормализация старого nested TLS должна сохранять pins/ECH и корректные типы
    полей. Штатный JSON v3.10.2 уже выдаёт их плоскими; не строить транспортные
    настройки заново и не подменять fingerprint/ALPN/Mux без отдельной причины.
13. При включённом HWID сохранить требуемые request headers панели и нужные
    X-Hwid-* ответы. Согласовать ProviderID и используемые Happ management headers.
    Текущая HTTP allowlist middleware их не сохраняет полностью.

## Приёмка реализации

Проверить в используемых версиях Happ на iOS и Android, затем в мобильной сети:

- Обнаружение A/B по remarks: латинские и кириллические метки, разный регистр
  и произвольный остальной текст. Смена ID балансеров не меняет выбранные роли.
- Отсутствие одной/обеих меток, дубликат роли, обе роли в одном названии,
  метка у обычного proxy-профиля → нет ошибочной композиции или выбора первой пары.
- A1 отказал, A2 работает, B работает → только A2 для новых VPN-соединений.
- Все A работают, B быстрее → только группа A.
- A1=300ms, A2=300ms, A3=2000ms, все измерены и доступны → A1 или A2.
- A1/A2 отказали, A3=2000ms доступен, B=100ms → A3, поскольку приоритет A строгий.
- Каждый A получил отрицательную пробу, B1 работает → B1.
- Все A отказали, B1 отказал, B2 работает → B2.
- Во время работы B восстановился любой A → новые соединения идут в A.
- Все A и B отказали → нет обходного перехода через freedom/direct.
- На запуске A ещё не проверены → B не включается из-за пустого отчёта.
- Смена Wi-Fi/LTE и выключение/включение ограничений → проверить обновление
  наблюдений и реальную задержку переключения.
- Отдельно проверить DNS, UDP, работу при Mux, сон/возобновление приложения,
  обновление подписки и сохранение direct/block-исключений.
- Для DNS на TCP/UDP port=53 проверить отдельно: быстрый A при доступных A;
  отказ одного A без перехода в B; отказ всех A с переходом в быстрый B;
  восстановление A с возвратом новых сессий. При отказе обоих пулов прямого DNS
  fallback быть не должно. Проверить отсутствие петли при loopback и дублей
  DNS-правила после повторного преобразования/обновления подписки.

Работа upstream Xray подтверждена также запуском официального Windows/amd64
v26.9.9 (52a412d, Go 1.27.1) с локальными SOCKS-узлами. Проверены холодный старт,
300/300/2000ms, отказ A по одному, приоритет последнего медленного A, переход к
быстрому B, отказ первого B, возврат A, полный отказ, DNS TCP/UDP и direct/block.
Оба iOS-режима проверены отдельно. VLESS с WS/gRPC/XHTTP из шаблона прошёл
xray run -test. CI повторяет эти проверки на официальном Linux v26.9.9.
Это не подтверждение встроенной LibXray на физическом iPhone: его проверки
из аудита, включая смену сети и сон, остаются этапом проверки на устройстве.

## Доставка профиля в Happ

SubscriptionFormatsTab задаёт JSON path, subJsonURI, always-array и автодетект
формата по User-Agent. ClientQrModal строит прямую JSON-ссылку как
subJsonURI + subId. Публичная JSON-ссылка должна вести на middleware, чтобы
пользователь получил составной профиль. Пункт Happ/crypt5 в интерфейсе сам по себе
не доказывает, что импортируется именно этот JSON URL: источник шифрованной ссылки
проверен отдельно: internal/web/service/happ.go::currentSource использует
subURI + subId, а не subJsonURI. Следовательно, правка только JSON URI не меняет
адрес, зашифрованный штатной кнопкой Happ. Нужен согласованный URL импорта через
middleware, включая обновление подписки и возможные new-url/fallback-url.

JSON endpoint v3.10.2 может отдать JSON с Content-Type=text/plain; view=raw
использует application/json. Обработка тела должна учитывать оба варианта.
При обычном subscription endpoint формат определяется также User-Agent и
настройками автодетекта. Accept=application/json сам по себе не является гарантией.

Отдельно согласуются Tunnel DNS Happ, dns.servers ядра и bootstrap DNS адресов
серверов. Beta port=53 не покрывает все три слоя. Наличие связанного Happ Routing
профиля меняет применимость dns-from-json-enable; его необходимо проверить
вместе с фактическими заголовками выдачи панели.

Наличие кода в ветке Happ-proxy/Xray-core main не устанавливает версию ядра,
которая встроена в конкретный установленный релиз Happ.

## Отложенная задача: техническая подпись Happ

Описание отложено пользователем 2026-10-24. См.
[проблему, доказательства и варианты](HAPP_BALANCER_DESCRIPTION_ISSUE.md).
Текущий первый blackhole сохраняется. Перестановка реального A на первое место
допустима только как отдельный прототип с проверкой поведения выхода по умолчанию,
всех отказов и DNS в passthrough / IOS-FIX / IOS-FIX-DNS. Реализация meta.serverDescription
не гарантирует отображение без необходимых возможностей ProviderID в Happ.
