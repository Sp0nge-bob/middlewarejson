# Сохранение технической подписи Happ через JSON

Дата: 2026-10-24. Исследование возобновлено по запросу пользователя.
Ниже — результаты исследования до реализации, не подтверждение совместимости
с мобильным приложением. По последующему запросу пользователя кандидат внедрён
в генератор/валидатор; точка отката — 64c0391 и тег
rollback-before-happ-subtitle-2026-10-24. Проверка UI устройств остаётся открытой.

## Вывод

Для подписки без ProviderID найден кандидат, сохраняющий блокировку при отсутствии
маршрута: отдельный **первый VLESS/WS/TLS outbound**, который никогда не соединяется
с внешним сервером, поскольку его dialerProxy указывает на настоящий blackhole.
Happ должен получить техническую подпись из его protocol/network/security.
Ожидание UI основано на разборе публичного Android APK; на телефоне не проверено.

Это развитие первоначального варианта «реальный A первым». В отличие от обычного
рабочего A, отдельный заблокированный выход не отправил запрос мимо балансера
при экспериментально вызванной ошибке маршрутизации.

Произвольный текст описания через этот способ не добавляется: подпись ограничена
распознанными Happ протоколом, транспортом и защитой. meta.serverDescription
по-прежнему требует соответствующих возможностей подписки в исследованном APK.

## 1. Что именно читает Happ

Повторно разобраны методы UI и перечисления в официальном Happ.apk 4.7.1:

- package su.happ.proxyutility, versionCode **1703**;
- SHA-256 `488923701e7d46e556b8566e50f03ef1b13ad807be0299feb892b83a2242a093`;
- у пользователя Android 4.7.1(**1999**); эта сборка недоступна в исследовании;
- iPhone Happ 6.0.0 / API 4.1.0 / Xray 26.9.9 не запускался.

В Ldx6.c для JSON UI читает `outbounds[0].protocol`. При распознанном типе
берёт `streamSettings.network`, `streamSettings.security` того же первого
выхода, проверяет их по перечислениям и добавляет локализованный суффикс JSON.
Поддержка VLESS, WS, TLS подтверждается перечислениями этого APK. Blackhole и
loopback не сопоставляются с пользовательским типом сервера. Поэтому изменение
одних streamSettings у первого blackhole не возвращает подпись.

Пользовательское описание из ServerConfig.Meta используется другой веткой UI:
для профиля в подписке она зависит от признака, вычисленного через status EXTRA.
Импортёр переносит root meta.serverDescription в ServerConfig.Meta, но это не
отменяет проверку при отображении. Для локальной группы без подписки условие
отличается; это не доказывает работу такой же строки в обновляемой подписке.

Документация описывает root meta.serverDescription в расширенных параметрах
с ProviderID. Заголовок/ProviderID не следует подделывать; активация определяется Happ.

## 2. Кандидаты и результаты

| Модификация JSON | Подпись без ProviderID | Влияние на маршруты | Решение |
|---|---|---|---|
| Root meta.serverDescription | Игнорируется UI исследованного APK для подписки без EXTRA | Граф не меняется | Оставить для клиентов с нужными возможностями, не считать универсальным решением |
| serverDescription в root/outbound/remarks как альтернативное поле | В исследованной ветке UI такого источника нет | Не устраняет проверку EXTRA | Нет подтверждённого пути |
| streamSettings у первого blackhole/loopback | Тип первого выхода не распознаётся | Не устраняет причину | Отбросить |
| Поставить рабочий A первым | Ожидается обычная техническая подпись | При отсутствии маршрута/ошибке балансера реально отправляет запрос прямо через A | Не рекомендовать для сохранения блокировки по умолчанию |
| Первый отдельный VLESS с dialerProxy → blackhole | Ожидается техническая подпись VLESS / WS / TLS | На стенде блокирует default/error path; реальные пулы и конечный blackhole сохранены | Основной кандидат на отдельную реализацию и проверку на устройствах |
| Старое outbound.proxySettings → blackhole | UI не решает несовместимость ядра | Xray 26.9.9 отвергает поле как удалённое | Не использовать; нужен sockopt.dialerProxy |
| Ручной импорт самостоятельного JSON-профиля | В публичном APK локальная группа может показывать custom meta | Меняет способ управления профилем; не решает поведение обновляемой подписки | Только диагностический вариант |
| Дублирующиеся JSON-ключи, несовместимые значения protocol | Нет переносимой гарантии парсинга | Разные парсеры могут выбирать разные значения или отвергать файл | Не применять |

## 3. Предлагаемая структура

Первые два выхода исследовательского варианта:

```json
[
  {
    "tag": "cf-description",
    "protocol": "vless",
    "settings": {
      "vnext": [{
        "address": "127.0.0.1",
        "port": 9,
        "users": [{
          "id": "00000000-0000-4000-8000-000000000001",
          "encryption": "none"
        }]
      }]
    },
    "streamSettings": {
      "network": "ws",
      "security": "tls",
      "tlsSettings": {"serverName": "localhost"},
      "wsSettings": {"path": "/"},
      "sockopt": {
        "domainStrategy": "AsIs",
        "dialerProxy": "cf-unavailable"
      }
    },
    "mux": {"enabled": false}
  },
  {"tag": "cf-unavailable", "protocol": "blackhole", "settings": {}}
]
```

Это фрагмент outbounds, не готовая подписка A/B. Первый служебный выход — валидный
VLESS, явно заблокированный цепочкой, а не переименование blackhole в VLESS.
Адрес loopback и AsIs исключают необходимость разрешать домен внешнего узла
для этого выхода. Технические поля для подписи можно брать из первого A только
при наличии отдельной политики поддерживаемых транспортов; нельзя слепо переносить
его sockopt, mux, цепочки, внешние адреса и bootstrap-настройки.

Остальные реальные A/B, их credentials, transport/TLS и сервисные loopback остаются
неизменными. cf-description не входит в selectors балансеров/observatory, не
используется в пользовательских правилах и не становится fallback B. Все реальные
отказы B по-прежнему направлены прямо в cf-unavailable.

При правильном маршруте: клиент → A/guard/B → реальный узел.
При отсутствии маршрута: клиент → cf-description → dialerProxy → cf-unavailable.
Нельзя направлять cf-description обратно в себя или в loopback, который снова
приведёт к этому default: это может создать цикл.

## 4. Что проверено на официальном Xray 26.9.9

Бинарник: 52a412d, go1.27.1, Windows amd64. Все сетевые стенды — loopback.
Публичные VPN-узлы, подписки и внешние probe endpoint не использовались.
Проведены 24 исследовательских сценария/проверки, не новый набор тестов приложения:

Обезличенные [результаты в JSON](research/happ-subtitle-xray26.9.9-results.json)
сохранены вместе с отчётом. Дополнительно оба профиля демонстрационного JSON
прошли `xray run -test`; отображение в Happ этим не проверяется.

### Выход по умолчанию и ошибка маршрутизации — 6 сценариев

В одном варианте routing.rules пуст, во втором правило указывает на roundRobin
с selector, не выбирающим ни одного outbound, без fallback. Оба JSON приняты ядром.

| Первый выход | Нет совпавшего маршрута | Ошибка выбора балансера |
|---|---|---|
| blackhole | Запрос заблокирован; 0 попыток к узлам | Запрос заблокирован; 0 попыток |
| рабочий A1 | Получен ответ A1; 1 попытка | Получен ответ A1; 1 попытка |
| отдельная SOCKS-копия с dialerProxy → blackhole | Запрос заблокирован; 0 попыток | Запрос заблокирован; 0 попыток |

### Приоритет и DNS — 2 сценария с несколькими фазами

Проверены рабочий A первым и отдельная заблокированная копия. Локальные реальные
пулы представлены SOCKS-узлами, чтобы измерять выбранный выход. Задержки:
A1/A2/A3 = 40/70/400 мс, B1/B2 = 20/80 мс. Для обоих вариантов:

- выбирается быстрый A, несмотря на более быстрый B;
- при отказе A1/A2 остаётся A3, несмотря на его 400 мс;
- после отказа всех A выбирается B1;
- после восстановления A2 новые соединения возвращаются к A2;
- TCP/UDP port 53 следуют A → B → A;
- при полном отказе запросы блокируются, UDP ждёт timeout, новых попыток
  пользовательского трафика к реальным узлам нет.

Это маршрутизация payload на порту 53, не полноценное разрешение DNS Happ.
Использованы локальный HTTP probe и interval 0.1s исключительно для стенда.

### Парсер реальных транспортов — 6 проверок

JSON с настоящими структурами VLESS/WS/gRPC/XHTTP и обоими вариантами первого
выхода принят `xray run -test` для passthrough, IOS-FIX, IOS-FIX-DNS.
Нормализация режима выполнена **до** исследовательской модификации outbounds.
Это проверка финального JSON ядром, а не совместимость текущего валидатора middleware.

### Именно VLESS/WS/TLS — 9 runtime-проверок

Для каждого из трёх режимов endpoint первого VLESS заменён локальным TCP-счётчиком.
Сценарии: dialerProxy на blackhole, dialerProxy на отсутствующий tag, контроль без
dialerProxy. Routing пуст, то есть используется именно первый выход.

- С blackhole: 0 TCP-соединений к endpoint во всех трёх режимах.
- С отсутствующим tag: 0 соединений; ошибка не вызвала прямой dial в этой версии.
  Отсутствующий tag не предлагается для рабочей реализации.
- В контроле без цепочки: по 5 TCP-соединений к счётчику; это подтверждает,
  что счётчик видит попытки, когда блокировка действительно снята.

### Удалённый proxySettings — 1 проверка

Парсер отклонил outbound.proxySettings и указал замену streamSettings.sockopt.dialerProxy.

Артефакты и JSON-результаты локального исследования находятся в
`.test_tmp/happ-4.7.1-inspect/outbound-results/`. Не считать 24 сценария проверкой
всех отказов всех транспортов/всех режимов или тестированием мобильного LibXray.

## 5. Что требуется для реализации

На этапе исследования validate_allowlist_profile требовал первый cf-unavailable
и отвергал дополнительный proxy вне пулов. В новой реализации разрешён только
полностью фиксированный служебный cf-description; произвольная ручная перестановка
или подмена его настроек по-прежнему отвергаются.

1. Добавить отдельный разрешённый cf-description с жёсткой проверкой всего
   служебного конфига, IP loopback, AsIs, mux off и dialerProxy → blackhole.
   Не разрешать произвольные цепочки в исходных пулах.
2. Проверять, что selectors A/B и observatory не захватывают cf-description;
   правила и fallback не направляют в него рабочие соединения.
3. Сохранить настоящий terminal blackhole и порядок service/DNS правил.
4. Обновить распознавание графа, идемпотентность и оба iOS-нормализатора так,
   чтобы они сохраняли служебный dialerProxy без перестройки fallback.
5. Выполнить регрессию cold start, direct/block, A/B/full failure, recovery,
   DNS TCP/UDP, ошибки маршрутизации, selectors, mux, malformed metadata/графа.
6. Подтвердить импорт, подпись, ping, запуск туннеля, DNS-from-JSON и работу
   после обновления подписки на Android 4.7.1(1999) и iPhone Happ 6.0.0.
   Проверить sleep/resume и Wi-Fi/LTE, а не только парсинг JSON.

Для безопасной проверки только подписи создан
[демонстрационный JSON](research/happ-subtitle-display-demo.json). Оба профиля
блокируют весь трафик, серверов VPN в них нет. Импортировать можно только как
отдельную диагностику UI; не заменять ими рабочую подписку и не подключаться
для доступа в интернет. Отсутствие meta.serverDescription проверяет именно
обычную техническую подпись, а не расширенный кастомный текст.
