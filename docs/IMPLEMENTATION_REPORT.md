# БС-балансер: реализация и проверки

Дата: 24 октября 2026 года. Версия приложения: 1.1.0.

## Точка отката

До реализации функции выполнены коммит и push всех текущих изменений,
включая переименование IOS-FIX-BETA → IOS-FIX-DNS и старые алиасы режима.
Опубликован [GitHub Release v1](https://github.com/Sp0nge-bob/middlewarejson/releases/tag/v1)
на коммит b444481504ac4e5ab0470a8e72c8ce97f63518cc. На этой версии прошли 59 тестов.
Тег не перемещается при дальнейших обновлениях. Инструкция отката: RELEASE_V1.md.

## Что реализовано

- Отдельная функция compose_allowlist_balancer, не новый режим трансформации.
- Поиск ровно одного балансера [A]/[А] и одного [B]/[В] в remarks, независимо
  от регистра, остального названия, порядка документов и ID панели.
- Пара заменяется одним профилем; остальные документы подписки сохраняются.
- Проверка реальных участников по selectors, коллизий тегов, одинаковых
  конфигураций подключений, согласованности DNS/inbounds/policy/routing.
  Неполная, неоднозначная или неподдерживаемая пара не объединяется; причина
  записывается в журнал. Никаких серверов из другого источника не добавляется.
- leastPing A → roundRobin guard A → leastPing B, два loopback, blackhole,
  один ordinary observatory для реальных узлов. Холодный старт не означает отказ A.
- DNS TCP/UDP:53 входит в ту же схему после двух служебных inboundTag-правил.
  Отказ обоих пулов не создаёт прямой DNS fallback. Пользовательские direct/block
  исключения для остальных направлений сохраняются.
- IOS-FIX и IOS-FIX-DNS валидируют готовый граф и сохраняют его fallback,
  observatory и порядок DNS. Повторная обработка не создаёт дубли.
- Первый SOCKS получает loopback bind; при переименовании mixed → socks
  обновляются routing inboundTag. Вложенные TLS pins/ECH сохраняются,
  списки pins/verifyPeerCertByName приводятся к строкам схемы v26.9.9.
- Передаются необходимые HWID и Happ headers; HWID-диагностика сохраняется
  также при HTTP 404 от панели. Authorization/Cookie/произвольный Host не пересылаются.

## Управление

ALLOWLIST_BALANCER_ENABLED=true по умолчанию. Само наличие корректных меток —
условие применения, поэтому немаркированные подписки не объединяются.
Независимый переключатель доступен в интерактивном меню и командах:

```bash
python -m app.cli settings allowlist-balancer on
python -m app.cli settings allowlist-balancer off
python -m app.cli settings transform-mode ios-fix-dns
```

Значения CLI хранятся в SQLite, имеют приоритет над .env и применяются к следующим
запросам без перезапуска. Выключение функции не меняет режим IOS-FIX.
Полностью неизменённый JSON: passthrough + выключенный БС-балансер.

Probe URL задаётся ALLOWLIST_PROBE_URL, только HTTPS; пауза между раундами —
ALLOWLIST_PROBE_INTERVAL_SEC, 1–3600 секунд, по умолчанию 20. Это не обещание
переключения ровно за 20 секунд. Проверки продолжаются при работе через B.

Runtime-стенд использует локальные SOCKS-узлы с управляемой задержкой и отказами.
Они возвращают идентификатор выбранного узла. Проверена маршрутизация трафика
на TCP/UDP-порту 53, а не полноценное разрешение имён через DNS Happ.
HTTP probe и interval=0.1s применяются только внутри изолированного теста;
генератор production-профиля требует HTTPS и использует настройки выше.

CI скачивает официальный Linux Xray v26.9.9 и запускает весь набор, включая
runtime-сценарии. Локальный запуск полного набора:

```powershell
$env:XRAY_TEST_BINARY = 'E:\AIPROJECTS\middlewarejson\.test_tmp\xray-v26.9.9\core\xray.exe'
$env:DB_PATH = 'E:\AIPROJECTS\middlewarejson\.test_tmp\http-tests.db'
```

## Что остаётся проверить на iPhone

Эталон пользователя: Happ 6.0.0 / Xray 26.9.9 / API 4.1.0. Закрытая библиотека
и Network Extension не запускались в этой среде. После импорта конечного профиля
нужны проверка Tunnel/Bootstrap DNS, реальные серверные транспорты, Wi-Fi/LTE,
сон/возобновление и длительная работа с недоступными A. Риск XHTTP из Happ #8
учитывается при этой проверке и по согласованию не блокирует обновление.

Существующие соединения не мигрируют; возврат к A действует для новых сессий
после успешной пробы. «Самый быстрый» означает минимальную измеренную задержку
наблюдателя, а не гарантированную скорость загрузки. Во время холодного старта
самый быстрый узел ещё неизвестен. HTTP-проба не подтверждает работу всех UDP-сервисов.

## Дополнение: имя и флаг профиля

Добавлены независимые настройки ALLOWLIST_BALANCER_NAME и ALLOWLIST_BALANCER_FLAG.
Например, `Мой VPN` + `RU` даёт `🇷🇺 Мой VPN`; пустой код или `off` оставляет
профиль без добавляемого флага. Настройки доступны в .env, CLI и интерактивном
меню; SQLite имеет приоритет. Смена имени/флага не меняет граф и режим IOS-FIX.
Изменение становится видно в Happ после обновления подписки.

### Исправление кодировки названия

Исправление обратимых UTF-8/Windows-1251 и Latin-1/Windows-1252 ошибок вынесено
из интерактивного CLI в общий модуль. Нормализация имени использует его при
сохранении через команду и меню, чтении .env и ранее записанного значения БД.
Поддерживается до трёх слоёв ошибочного декодирования. Применяется только
строгое обратное преобразование; утраченные или заменённые символы не угадываются.
Сохранённая строка БД при чтении не перезаписывается; исправляется отображаемое
имя. Для необратимо повреждённого значения требуется повторная установка имени.
У команды `settings allowlist-balancer-name` добавлен явный `--unicode-escaped`:
JSON-escape позволяет передать точное Unicode-имя ASCII-командой независимо
от кодировки терминала. Обычный ввод не интерпретирует escape-последовательности.

### Описание профиля Happ

**Уточнение 2026-10-24:** пользователь не наблюдает подпись на Android
4.7.1(1999), ProviderID не настроен. Отправка поля не гарантирует отображение.
Задача отложена; [результаты исследования и методы решения](HAPP_BALANCER_DESCRIPTION_ISSUE.md).
Позднее пользователь возобновил исследование: выполнены 24 локальных сценария
для JSON-кандидатов и upstream Xray 26.9.9. Результаты и ограничения вынесены
в [отдельный отчёт](HAPP_JSON_SUBTITLE_RESEARCH.md). Production-код не изменён.

Добавлена независимая настройка ALLOWLIST_BALANCER_DESCRIPTION и ключ SQLite
allowlist_balancer_description. CLI: `settings allowlist-balancer-description`,
интерактивные настройки: пункт 6. Значение `auto` (по умолчанию, также пустая
строка) сохраняет meta.serverDescription исходного A; при отсутствии описания
строит подпись вида `VLESS / WS / TLS | JSON` из первого узла A. Свой текст
передаётся напрямую в meta.serverDescription с общей обработкой кодировки.
Поддерживается явный флаг --unicode-escaped. Изменения через SQLite применяются
к следующим ответам подписки; .env требует перезапуска службы.

На этом этапе первый blackhole и граф A → Б сохранялись. Различие serverDescription между
исходными A/B допустимо; остальные поля meta должны совпадать и сохраняются.
Подпись статична и не отражает выбранный наблюдателем узел. Трансформации
IOS-FIX / IOS-FIX-DNS сохраняют meta как часть исходного документа.
Используется документированное Happ поле:
https://github.com/HappDev/happ_su/blob/main/dev-docs/examples-of-links-and-parameters.md#5-visualization-and-metadata

### Реализация технической подписи без ProviderID

Перед изменениями опубликованы checkpoint-коммит **64c0391** и тег
**rollback-before-happ-subtitle-2026-10-24**; см. [откат](ROLLBACK_HAPP_SUBTITLE.md).

Первый outbound теперь фиксированный `cf-description`, VLESS/WS/TLS с loopback
127.0.0.1:9, AsIs, отключённым mux и единственной цепочкой dialerProxy → cf-unavailable.
Реальные адреса, UUID, TLS/transport-настройки A/B в него не копируются. Настоящий
cf-unavailable / blackhole сохранён, fallback B продолжает указывать прямо в него.
Статическая техническая подпись не отражает транспорт выбранного реального узла.
Кастомное meta.serverDescription остаётся независимым механизмом и сохраняет
ограничения возможностей Happ/ProviderID.

Валидатор требует полного совпадения служебного outbound с фиксированным шаблоном,
запрещает его захват pool selectors, observatory и рабочими routing rules, а также
произвольные цепочки у остальных выходов. Старый граф без cf-description с первым
blackhole продолжает проходить валидацию и оба iOS-нормализатора. CLI не учитывает
служебный VLESS как дополнительный реальный сервер. Повторная трансформация
сохраняет граф и служебный выход; source pool chains по-прежнему не разрешаются.

Полный локальный набор: **223 passed**, 1 прежний StarletteDeprecationWarning,
включая официальный upstream Xray 26.9.9 (52a412d, Windows amd64).

- 3 проверки парсера с реальными структурами VLESS/WS/gRPC/XHTTP;
- 3 полных runtime-сценария (passthrough, IOS-FIX, IOS-FIX-DNS): cold start,
  быстрый A, медленный последний A, отказ всех A, отказ B1, восстановление A,
  DNS TCP/UDP, полный отказ и direct/block;
- 6 runtime-сценариев ошибок (3 режима × нет маршрута/ошибка балансера): TCP,
  TCP port 53 и UDP port 53 блокируются; журнал подтверждает перенаправление
  VLESS-dial на настоящий cf-unavailable;
- проверки повреждений служебного выхода, его selectors/observer/rules,
  порядка default, запрета дополнительных цепочек, старого графа и CLI-счётчика.

Это не подтверждение UI Android 4.7.1(1999), iPhone Happ 6.0.0 или мобильного
LibXray. На устройствах остаются импорт/обновление подписки, подпись, ping,
Tunnel/Bootstrap DNS, sleep/resume, Wi-Fi/LTE и реальные транспорты под нагрузкой.
