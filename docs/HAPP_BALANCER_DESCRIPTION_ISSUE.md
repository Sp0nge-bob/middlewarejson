# Пустая подпись БС-балансера в Happ

Дата: 2026-10-24. Статус: отложено по решению пользователя; косметическая проблема.
Изменение маршрутизации ради подписи сейчас не выполнять.

## Наблюдение и окружение

У составного профиля отсутствует строка под названием, тогда как обычные узлы
показывают `VLESS / WS / TLS | JSON`. Пользователь сообщил о сохранении проблемы
после добавления meta.serverDescription в middleware (коммит ba70868).

- Наблюдаемый клиент: Android Happ 4.7.1(1999), сведения пользователя.
- ProviderID у подписки не настроен, подтверждено пользователем.
- Эталон iPhone: Happ 6.0.0 / API 4.1.0 / Xray 26.9.9. Отображение подписи на
  этом устройстве в рамках расследования не проверялось.
- В конфигурации middleware первым outbound стоит cf-unavailable / blackhole.
  Он служит выходом по умолчанию при отсутствии маршрута. Рабочий граф:
  leastPing A → guard A → leastPing B → blackhole.

Пустая подпись сама по себе не доказывает ни отказ, ни корректность балансировки.

## Подтверждённые сведения и пределы вывода

1. Документация Happ указывает JSON-поле `meta.serverDescription` для замены
   технической подписи. Параметр находится в разделе расширенных возможностей,
   для которого требуется ProviderID; указан предел 30 символов.
2. ProviderID привязывается к домену подписки. Наличие идентификатора в JSON или
   заголовке само по себе не доказывает активацию расширенных возможностей.
3. Исследован официальный Happ.apk из GitHub-релиза 4.7.1:
   - package: su.happ.proxyutility;
   - versionName: 4.7.1; versionCode: **1703**, а не пользовательский 1999;
   - SHA-256: `488923701e7d46e556b8566e50f03ef1b13ad807be0299feb892b83a2242a093`.
4. Статический разбор DEX этой сборки показывает:
   - Lut2.a импортирует meta.serverDescription из XRayConfig в метаданные ServerConfig;
   - SubscriptionItem.b0 возвращает true при status == EXTRA;
   - Lwn4.F передаёт признак в поле Loo7.g (для локального профиля без подписки
     ветка отличается; проблема здесь относится к профилю внутри подписки);
   - Ldx6.c использует пользовательскую подпись при наличии текста и включённом
     признаке; иначе для JSON читает protocol первого outbound и формирует
     техническую подпись из его protocol/network/security;
   - если protocol не сопоставлен с поддерживаемым типом сервера, текст может
     оказаться пустым. Это согласуется с первым blackhole нашего профиля.
5. Xray документирует первый outbound как выход по умолчанию при отсутствии
   или неудаче выбора маршрута. Его перестановка меняет поведение конфигурации.

Это подтверждает механизм в публичном APK 4.7.1(1703) и объясняет наблюдение
пользователя без ProviderID. Точная сборка 4.7.1(1999) не исследована, UI на
устройстве не воспроизведён. Не считать ограничение доказанным для всех версий
Android/iOS или соответствующим конкретному коммерческому тарифу Happ.

APK и инструменты анализа находятся в игнорируемой .test_tmp; в Git они не входят.
Для повторного получения: `gh release download 4.7.1 --repo Happ-proxy/happ-android --pattern Happ.apk`.
Следует повторно сверять хеш и manifest, поскольку ассеты релиза могут заменяться.

## Возможные решения

| Метод | Ожидаемый результат | Условия и ограничения | Статус |
|---|---|---|---|
| Настроить ProviderID для домена и активировать необходимые возможности Happ | Кастомная подпись через уже реализованное meta.serverDescription; граф не меняется | Проверить фактический статус подписки и доставку заголовка providerid. Для точного клиента подтвердить результат; одной регистрации недостаточно | Документированный путь с подтверждённой проверкой EXTRA в публичном APK |
| Поставить реальный A первым outbound | Автоматическая техническая подпись по первому узлу без кастомного описания | Меняется выход по умолчанию. Нужны полное покрытие TCP/UDP правилами, сохранение DNS/loopback порядка и конечного blackhole, проверка отказа маршрутизации. Подпись статична даже при выборе другого A или B | Кандидат на прототип, не реализован и не признан безопасной заменой |
| Исправление UI Happ: искать первый поддерживаемый proxy-outbound только для подписи | Техническая подпись при сохранении первого blackhole в JSON | Требует изменения клиента разработчиками Happ. Подготовить обезличенный минимальный JSON и сравнение с обычным профилем. Сообщение разработчикам не отправлялось | Предпочтительный вариант со стороны клиента, доступность не подтверждена |
| Добавить короткую информацию в remarks | Информация видна в заголовке без зависимости от serverDescription | Не возвращает отдельную строку. Длинное название обрезается; доступно уже существующей настройкой имени | Временный способ отображения |

Обновление Happ или повторный импорт подписки — диагностические эксперименты,
а не подтверждённые решения. Они не отменяют проверку статуса, найденную в APK.
Не подменять protocol blackhole на VLESS ради подписи и не добавлять фиктивный
сервер: это меняет смысл выхода и затрудняет диагностику графа.

## Порядок работ при возвращении к задаче

1. Получить точный APK/источник сборки 1999 либо воспроизвести поведение на устройстве.
2. Проверить фактический ответ middleware: meta.serverDescription, Content-Type,
   версию запущенного процесса, заголовок providerid. Сохранять только обезличенные
   данные, исключая UUID, адрес подписки, HWID и ключи серверов.
3. Если выбран ProviderID — подтвердить доменную привязку и активный статус в Happ,
   затем проверить обновление существующей подписки и отдельный свежий импорт.
4. Если выбран первый реальный A — сначала реализовать изолированный прототип,
   усилить валидацию итогового правила и исследовать ошибки выбора маршрута.
   Прогнать cold start, leastPing, частичный/полный отказ A, отказ B, отказ обоих
   пулов, возврат A, DNS TCP/UDP, direct/block и loopback во всех трёх режимах.
   Проверить отсутствие обхода A → B при ошибках и несовпадении маршрутов.
5. Подтвердить подпись и маршруты на Android 4.7.1(1999) и эталонном iPhone.
   Успешный `xray run -test` не подтверждает работу UI Happ.

Сейчас новых runtime-тестов и изменений графа для этой проблемы нет.
